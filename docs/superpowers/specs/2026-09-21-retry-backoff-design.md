# 故障转移的重试退避（同上游才等）

日期：2026-09-21
状态：已实现

## 背景

站主反馈：**故障转移时零间隔连打上游，会被上游当成攻击，直接触发熔断。**

现状核实（`backend/internal/relay/service.go` 的 `Relay` 主循环）：

- 失败后是裸 `continue`：网络层失败一处、上游非 2xx 一处，**两处之前都没有任何等待**。
  `time.Sleep` 在整个 relay 包的**非测试代码里出现 0 次**。
- 已有的保护（`applyCooldown`、`markChannelFailure` 连击熔断）都作用于
  **后续请求**能不能选中这条渠道，而不是**当前请求**下一次尝试的间隔。
- `defaultServerErrorCooldown` 的注释恰好点出了这个需求 ——
  「上游 5xx 时的短退避，**避免立刻把同一个故障实例再打一遍**」——
  但作者用的是「事后冷却」，不是「事前延迟」。

线上数据佐证这是真实场景：

| 事实 | 数据 |
|---|---|
| 同一上游被两条渠道共用 | `https://d1api.xin/v1`：id=521（分组268 权重2）、id=359（分组20 权重2） |
| 最近的重试 | 3 次（`retry_count` 1~2），全部 **403**（Cloudflare `Error 1010`） |

只要某把密钥同时允许分组 20 与 268，故障转移就会**零间隔**把同一份请求
连打给同一个上游两次。对上游而言，这与「同一个账号被重试」没有区别。

## 参考实现：sub2api

站主指定参考 `github.com/Wei-Shaw/sub2api`（核心 `backend/internal/handler/failover_loop.go`）。

它的核心是**二分法**：

| 动作 | 是否等待 | 值 |
|---|---|---|
| 重试**同一个账号**（`RetryableOnSameAccount`） | 等 | `sameAccountRetryDelay = 500ms`，请求级瞬时错误再 ×2 递增，封顶 `maxRequestScopedRetryDelay = 8s` |
| 切到**另一个账号** | **默认不等** | 仅 Antigravity 平台有 `(SwitchCount-1)×1s` 线性延迟（OAuth 账号池特性） |
| 会话池选中耗尽（503） | 等 | `singleAccountBackoffDelay = 2s` |
| 429 | 等 | 读 `Retry-After`，封顶 8s，且不越过 deadline |

其他可借鉴的取舍：

- 池模式可重试状态码白名单只有 **401/403/429**，**不含 5xx**（5xx 直接换账号）。
- 所有等待都走 `sleepWithContext`：`ctx` 取消立即返回，不是裸 `time.Sleep`。
- 429 的 `Retry-After` 有**双重用途且分开封顶**：作为当前请求的等待时长（封顶 8s）、
  作为渠道摘除的冷却时长（上限 24h）。两个上限服务两个不同对象，故意不同值。

## 关键决策：判据是「同一上游」而不是「同一渠道」

这是照搬 sub2api 时必须做的适配，也是整个设计里最容易搞错的一点。

| | sub2api | llm-relay |
|---|---|---|
| 资源单位 | **账号**（多个账号共用同一上游） | **渠道**（各自独立的上游地址） |
| 会重试同一资源吗 | 会（`RetryableOnSameAccount`） | **不会** —— `filterTried` 按渠道 ID 去重（`router.go`） |
| 「打同一个上游」如何发生 | 同账号重试 | **不同渠道共用同一个 `base_url`** |

所以 sub2api 的「同账号」在 llm-relay 里的对应物**不是**「同一个渠道」，
而是**同一条上游路径**。判据：`base_url` 的 `host[:port]` 相同**且**出口代理相同
（同一域名经不同代理出去，上游看到的来源不同，不算同一路径）。

**为什么不做成「每次重试都等」**（站主最初的字面要求）：

1. 换到不同上游时，被切走的那台上游**根本不知道**我们重试了 —— 等待买不到任何东西。
2. 代价却是实打实的：`max_retries=2` 时最坏 +1s，且**等待期间全局并发闸门的名额
   仍被占着**（`relay_handler.go` 在整个请求期间持有）。上游大面积故障时，
   一批请求同时睡下会把闸门（默认 64）睡满，把「上游慢」放大成「本地 429」。
3. 站主已有「延迟 2 秒」的直觉，`RELAY_RETRY_SAME_UPSTREAM_DELAY` 可调；
   但默认只对同上游生效 —— 把触发面收敛到唯一真正会造成伤害的那条路径。

## 实现

新文件 `backend/internal/relay/backoff.go`：

| 函数 | 职责 |
|---|---|
| `UpstreamHost(baseURL)` | 取归一化的 `host[:port]`，**字符串切分而非 `net/url`**（见下） |
| `retryHop` / `hopOf` | 「刚失败的那一次」的快照（渠道、主机、代理、状态码、Retry-After） |
| `sameUpstream(prev, next)` | 判据：同 host **且**同出口代理 |
| `retryDelayFor(prev, next, opts)` | 算出等待时长；0 = 不等 |
| `withJitter(d)` | ±25% 抖动 |
| `waitBeforeRetry(ctx, d)` | 可被 ctx 打断的等待 |

插入点在 `Relay` 主循环**开头**（`cand := cands[0]` 之后、记账与抢名额之前），
而不是两处 `continue` 之前。理由：

1. **「下一个候选是谁」在失败那一刻还不知道** —— `filterTried` 会跳过滤掉刚进冷却的
   渠道（而 `applyCooldown` 恰在 `continue` 前把当前渠道打进冷却），分组额度裁剪也会
   往后剥。必须在下一轮开头重算。
2. 一处覆盖两个失败分支，避免「两份手抄迟早漂移」。
3. 在 `groupLimit.Record` 之前 → RPM 口径不变（仍是「真正发往上游的请求数」）。
4. 在 `AcquireWait` 之前 → 等待期间不占渠道并发名额。
5. 候选耗尽走 `break`，**最后一次尝试之后不会白等**。

需要新增 `prevHop` 变量而非复用既有的 `lastCand`：后者的语义是「最后一次**拿到上游
应答**的失败尝试」（网络层失败时刻意不更新），而退避判定需要包含网络层失败在内的
「刚失败的那一次」。

### 为什么用字符串切分而不是 `net/url`

用户常填 `d1api.xin/v1` 这类**不带 scheme** 的地址（`proxy.go` 的 `Validate` 专门拒绝
`http://host` 这种写法，反证这类填法真实存在）。`url.Parse` 对无 scheme 的串会当相对
路径解析，`Hostname()` 返回空 —— 于是两条共用同一上游的渠道被判成不同主机，
退避**悄悄失效且没有任何报错**，正是本仓库最忌讳的静默失真。

字符串切分没有这种失败模式：最坏情况是返回空串，判为「不同上游」，
是个安全方向的误判（少等一次）而非错等。

### 抖动

`±25%`，硬编码不做成配置（它不是策略，是让退避真的起作用所必需的噪声）。

为什么 sub2api 的同账号重试没有而这里必须有：那边默认基数 500ms、账号池很大，
齐射被池子摊开了；而**上游故障是上游级的**，会被同一时刻的所有并发请求同时撞上。
等待时长完全相同时，这批请求会在同一毫秒再次一起打向同一台上游 ——
退避反而把一次冲撞变成了周期性齐射，那恰恰是本功能要消灭的形态。

取 ±25% 而非全抖动（0~d）：下限保证确实等了一会儿，上限不改变量级；
全抖动会让「这次请求为什么慢」在日志里失去可解释性。

## 已知边界（设计决策，未修）

- **域名与 IP 别名判不出同一上游**。`d1api.xin` 与它的裸 IP 会判为不同上游 → 不延迟。
  不做 DNS 反查：那会把转发路径变成 DNS 阻塞点。线上那对渠道用的是同一个字符串 URL，
  不受影响。
- **不区分状态码**（401/403 也等）。401/403（密钥失效、被 CF 拦截）等 500ms 对
  「上游压力」确实没有改善，但为单一状态码开分支会让「什么时候会等」需要查表 ——
  而这条规则的价值正在于可解释。线上那 3 次 403 换的都是**不同上游**，
  走的是「不延迟」分支，不受影响。
- **不做递增退避**。sub2api 的指数递增是因为它在同一账号上重试 3 次；
  llm-relay 的 `maxAttempts=3`、同主机最多 2 次，递增带来的差别（500ms vs 1s）
  不值得让行为失去确定性。封顶常量已摆在那里，将来要加不改变现有语义。
- **等待期间持有全局并发闸门名额**（见上文的代价分析）。这是本改动最主要的代价，
  也是「跨上游不延迟」的理由。

## 验证

- **单元测试** `backoff_test.go`：判据与边界的纯函数测试（无需 DB）。
  含「换上游必须为 0」这个防回归的核心断言，以及「`Options{}` 全零时一切不等待」
  这个向后兼容的硬保证。
- **端到端** `scripts/test-retry-delay.py`（配 `scripts/flaky-upstream.js`）：
  用**上游侧记录的相邻两次请求到达间隔**作为判据，而非客户端总耗时
  （耗时里混着连接建立与调度噪声，无法区分「等了一会儿」与「上游慢」；
  这与 `slow-upstream.js` 用并发峰值而非耗时证明名额语义是同一判据思想）。

  实测结果：

  | 场景 | flaky 收到 | 到达间隔 | 总耗时 |
  |---|---|---|---|
  | A 两条渠道共用同一上游 | 2 次 | **416ms** | 0.66s |
  | B 两条渠道指不同上游 | 1 次 | — | **0.01s** |
  | C 429 + `Retry-After: 1` | 2 次 | **926ms** | 1.14s |

  A 与 B 的对比直接证明核心设计：只有打同一上游才等。
